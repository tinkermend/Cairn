---

你现在不要继续开发新功能。

我希望你暂时切换角色：把自己当成一名刚刚接手该项目的资深软件架构师、Staff Engineer 和安全/性能审查人员，对当前项目进行一次“阶段性工程审计”。

背景：

这个项目最近连续进行了较多 AI 辅助开发。我担心虽然目前功能基本能够运行，但在连续快速迭代过程中，可能已经产生架构漂移、临时补丁、重复实现、隐藏 Bug、安全漏洞、性能隐患以及长期技术债。

这次任务不是继续修改代码，而是先进行系统性复查。

第一阶段：理解项目

首先阅读：

1. 项目 README / 架构设计文档 / 开发规范
2. package.json、pom.xml、requirements、配置文件等工程定义
3. 项目目录结构
4. 数据库 Schema / Migration
5. API 定义
6. 核心业务模块

然后通过 Git 历史重点分析最近 1～2 天的开发内容：

* git log
* git diff
* 最近新增文件
* 最近修改文件
* 最近删除/重构内容

先回答：

“最近这轮开发到底改变了系统什么？”

不要急于逐文件 Review。

请先建立：

原始架构 → 最近新增能力 → 新增模块 → 数据流变化 → API变化 → 数据模型变化 → 依赖变化

之间的整体关系。

第二阶段：检查架构是否发生漂移

重点判断最近开发是否正在让项目偏离原本设计。

检查：

* 模块职责是否仍然清晰
* 是否出现跨层调用
* 是否存在不合理依赖
* 是否重复实现已有能力
* 是否出现过大的 Service / Component / Module
* 数据模型是否开始混乱
* API 边界是否合理
* 前端/后端职责是否合理
* 状态是否存在多个事实来源
* 公共能力是否被散落实现
* 是否为了快速实现功能破坏了原有抽象

重点寻找 Architecture Drift。

对于发现的问题，请进一步判断：

这是合理演进，还是架构正在逐渐失控？

第三阶段：寻找隐藏 Bug

不要只检查语法错误和明显 Bug。

重点推演：

* 正常路径
* 异常路径
* 边界条件
* 空数据
* 大数据
* 网络失败
* 数据库失败
* API超时
* 重试
* 用户重复点击
* 并发请求
* 页面刷新
* 服务重启
* 部分成功/部分失败
* 状态恢复

重点寻找：

* Race Condition
* 状态不一致
* 幂等问题
* 事务问题
* 资源泄漏
* 异常未处理
* 错误被吞掉
* 数据覆盖
* 前后端契约不一致

第四阶段：安全审计

请以攻击者视角检查：

* Authentication
* Authorization
* 越权访问
* IDOR
* SQL Injection
* XSS
* CSRF
* SSRF
* 文件上传
* 路径穿越
* 命令执行
* CORS
* Token/Session
* API 参数校验
* Secret 泄露
* 日志敏感信息
* Debug接口
* 管理接口
* 第三方依赖风险

不要只检查传统漏洞。

结合本项目实际业务流程寻找：

“一个恶意用户能够通过怎样的操作顺序绕过系统原本的业务约束？”

第五阶段：性能与容量风险

不要以当前测试数据量判断性能。

请分别假设系统的数据量/任务量/并发量增长：

10倍
100倍
1000倍

推演系统首先会在哪里出现瓶颈。

重点检查：

* N+1
* 全表扫描
* 缺失索引
* 循环数据库操作
* 循环API调用
* 重复IO
* 重复计算
* 大对象
* 内存泄漏
* 无界缓存
* 无界队列
* 无界并发
* 请求瀑布
* 大JSON
* 前端重复渲染
* WebSocket堆积
* 日志爆炸
* 定时任务重叠

指出具体代码路径，而不是泛泛讨论。

第六阶段：AI开发技术债检查

重点寻找最近快速开发过程中产生的：

* Patch-on-Patch
* Workaround
* TODO / FIXME
* 临时兼容代码
* fallback
* duplicated logic
* magic number/string
* 无用旧代码
* 死代码
* 重复状态
* 多个事实来源
* 不必要的抽象
* 过度设计
* 为修复一个Bug而引入多个额外状态
* 可以删除而不是继续维护的代码

尤其关注：

“代码虽然能运行，但已经开始变得不敢修改”的区域。

第七阶段：测试完整性

分析现有测试真正覆盖了什么，而不仅仅看测试数量。

重点找：

“哪些重要行为现在完全依靠开发者认为它应该工作，而没有任何自动化证据证明它工作？”

检查：

* 核心业务流程
* 异常路径
* 权限边界
* 数据一致性
* 并发
* API契约
* 回归测试

输出要求

暂时不要修改任何代码。

先输出审计报告。

每个发现必须尽量包含：

【严重程度】Critical / High / Medium / Low

【问题位置】
具体文件、模块、函数、代码位置

【问题描述】
到底存在什么问题

【触发条件】
什么情况下会出现

【影响】
会造成什么后果

【证据】
为什么认为这是一个真实问题，而不是理论猜测

【建议方案】
应该如何解决

【是否建议立即处理】
是 / 否

最后给出：

1. 当前项目架构健康状况
2. 最近开发引入的主要变化
3. Architecture Drift 清单
4. Top 风险问题
5. 安全风险
6. 性能风险
7. 技术债
8. 测试缺口
9. 可以删除/合并/简化的代码
10. 下一阶段建议优先处理事项

重要要求：

不要为了显得审查全面而制造问题。

区分：

* 已确认问题
* 高概率风险
* 理论风险
* 单纯代码风格问题

优先寻找会真正影响生产环境的问题。

如果没有足够证据，请明确写“需要进一步验证”，不要把猜测描述成事实。
