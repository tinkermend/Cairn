# 识途 RunLease / Fencing / 恢复：执行所有权与最小观察面

日期：2026-09-11。状态：**已落地**。  
对应路线图 P3（Worker Queue、RunLease、Fencing），以及 RF06 / RF07 / RF08、S01、VS1、A03。  
前置：执行内核（P1 / P2，已落地）、目标系统目录（已落地）、对象存储内核（已落地，本方案不碰对象）、BrowserSession 第一截（已落地，本方案回填 `run_fencing_token`，不做 Affinity）。  
范围：让多个 Worker 竞争任务时只有一个有效执行所有者；崩溃、暂停、失联、DB 断连后能保守恢复；人能在控制台看见并结束一次 Mock Run。  
不是页面定位（P5）、不是截图 Trace（P6 其余）、不是 SSE（P7 正式实时面）、不是会话菜单、不是 Sequence Editor。

## 1. 为什么现在写

执行内核已经能跑 Echo → Delay → Fail，Run / StepRun / Attempt / Evidence 账本在库。会话第一截已经能纳管浏览器。缺的是**执行所有权**：

- `claimQueuedRun` 只有 `FOR UPDATE SKIP LOCKED`，没有 owner、没有 TTL、没有 fencing。Worker 被 kill 后 Run 停在 `RUNNING`，直到人工改库——P2 写明的限制，不是遗漏。
- 仓里没有 `workers` / `run_leases`。`session_leases.run_fencing_token` 仍是 `NULL`：只能证明「我拿着会话」，不能证明「我仍是这个 Run 的合法执行者」。
- `WAITING_FOR_AUTH` 占着该 Worker 的执行槽，因为没有「释放 RunLease、认证完成后再领取」。
- `NEEDS_REVIEW` 是终态，没有控制面出口。
- 控制台能管目标系统，**不能看见一次 Run**。场景与运行只有 API，首页仍写「将按功能方案逐步接入」。

没有这一截，M1「执行骨架可恢复」过不了；后面的 Affinity、浏览器步骤、SSE 观察面都没有合法持有者可绑。

### 1.1 没有页面，验收为什么不完整

后端单测能证明「两个事务只有一个领到租约」，**不能**证明产品闭环成立。识途的验收本来就不是单层：

| 层 | 证明什么 | 证明不了什么 |
| --- | --- | --- |
| L1 库与 Worker | 并发领取、旧 token 拒绝、崩溃接管、未知副作用停机、DB 断连不双写 | 人能不能看懂、权限按钮对不对、刷新后是否同一份事实 |
| L2 HTTP | 信封、鉴权、核查 / 取消 / 创建的领域码 | 3 Worker 竞争、丢租与迟到回调 |
| L3 控制台 | 状态、步骤、Attempt、证据能看见；取消与核查能点；刷新 GET 与库一致 | RF06 的 3×100×10、进程暂停、DB 断连 |

目标系统模块已经按这三层做完：Repository + HTTP spec + 真实页面。执行内核主动不做页面，是为了先冻账本，不是把「只测 API」定义成完整。P3 把账本补成可恢复的同时，补上 **VS1 的人机闭环**。

反过来：**有页面也不等于 P3 完成。** 点一次「运行成功」证明不了 fencing。RF06–RF08 必须在真实 PostgreSQL 上用多进程与故障注入跑；页面只消费 GET，不参与所有权判定。

因此本期 Gate = L1 ∧ L2 ∧ L3。缺一层就不得标完成。Gate 是一个，PR 可以是两个（§6）。

## 2. 目标与非目标

### 目标

1. 冻结 Worker 注册与心跳：`CAIRN_WORKER_ID` 每进程一份活实例；同 ID 双开启动失败。
2. 冻结 `run_leases`：获取 / 续租 / 释放 / 过期四条原子操作；同一 Run 同时只有一个 `ACTIVE` 租约；fencing token 由库递增，Worker 不得自造。
3. 新领取与恢复领取走**同一** `claimRun`：`QUEUED` 与「已无 ACTIVE 租约的 `RECOVERING`」一起竞争，`RECOVERING` 优先。
4. 所有 Worker 侧状态写入（Attempt、context、Evidence 关联、StepRun / Run 状态）必须在同一事务内**先锁 Run 行、再验租约**；过期或旧 token 0 行，不得改事实。
5. 丢租即停：续租失败后本进程立即停止该 Run，不重试同一 grant。
6. 恢复扫描对两类现场动手：过期租约，以及「`RUNNING` 却无 ACTIVE 租约」的漂移。孤儿 `RUNNING` Attempt 按 `effectType` 分流：`SIDE_EFFECT` 且结果未知 → `NEEDS_REVIEW`，不自动再做一次。反复丢租的 Run 有上限，超过进 `NEEDS_REVIEW`，不得无限抢先重领。
7. Worker 心跳过期 → Worker `LOST` → 其名下未关闭的 `browser_sessions` 进 `LOST`（接上会话方案 D4，不再只靠人工）。
8. `WAITING_FOR_AUTH` 释放 RunLease；认证恢复后重新领取并增代。`NEEDS_REVIEW` 提供人工结论出口。无租约状态（`QUEUED` / `RECOVERING` / `WAITING_FOR_AUTH`）的取消由控制面直接写终态，不留死角。
9. 回填 `session_leases.run_fencing_token`：新的 `ACTIVE` 会话租约必须带当前 Run fencing。
10. 最小观察面：场景列表 / 最小创建、运行列表 / 详情（步骤、Attempt、结构化证据）、创建 Run、取消、核查。刷新 GET 是页面事实源，只做手动刷新。

### 非目标

- 不做 Redis / Kafka、独立 Scheduler、跨区域调度。
- 不做 Affinity / Placement / 容量排队到指定 owner（P4 后半）。本方案任何健康 Worker 都可领取，容量满则本进程不领。
- 不做活会话跨 Worker 迁移；失联只把会话标 `LOST`，不关别人的浏览器。
- 不扩 `RUN_EVENT_TYPES`，不落 `run_events`，不发 PG NOTIFY / SSE。任务唤醒继续用 tick + 恢复扫描。
- 不做会话菜单、会话只读页、处置按钮（API 已有，观察面属 P7）。
- 不做 Sequence Editor、草稿/发布、Compiler、步骤拖拽、引用图。
- 不注册 Navigate / Click / AI 等 Step Type；Engine 仍不调用 `BrowserPort`。
- 不做截图、Trace、授权下载。
- 不做任何自动刷新。手动刷新 GET 是本期唯一进度通道，SSE 属 P7。

## 3. 决策

### D1. 三层验收一起交付，页面是观察面不是所有权面

控制台只做 GET 展示与三条有副作用的 POST（建场景、建 Run、取消、核查 / 认证恢复）。所有权、fencing、恢复**不得**出现在 React 状态机里。

页面刷新、切回窗口、点「刷新」都走已有 `GET /runs/:id`。**不做自动刷新**：宪法 §13 禁止把轮询当正常进度机制；L3 的全部验收都能用手动刷新走通，没有理由为了演示顺手开一条日后必须拆掉的通道。

浏览器验证（目标页既有体例）必须走通：登录 → 建最小场景 → 创建 Run → 详情看到步骤与 Attempt → 手动刷新等到终态 → 取消一条 QUEUED → 核查一条 `NEEDS_REVIEW`。这是 L3，不能代替 L1。

### D2. RunLease 独立成表，不把租约列摊进 `runs`

与 `session_leases` 对称：租约有历史、有换代、有释放原因；Run 行继续只表达业务状态。`RUNNING` 与「谁持有」不是同一件事——`WAITING_FOR_AUTH` / `RECOVERING` 都是 Run 状态，但此时不应有 `ACTIVE` 执行租约。

派生不变量（Repository + 测试卡住，跨表 CHECK 做不到；第一条若漂移，由 D8 的漂移扫描拉回 `RECOVERING`，不是只靠断言）：

```text
RUNNING            ⇒ 恰好一条 ACTIVE run_lease
RECOVERING         ⇒ 0 条 ACTIVE
QUEUED             ⇒ 0 条 ACTIVE
WAITING_FOR_AUTH   ⇒ 0 条 ACTIVE
终态               ⇒ 0 条 ACTIVE
同一 run_id        ⇒ 至多一条 ACTIVE   // 部分唯一索引
```

### D3. Worker 心跳 ≠ Run 续租 ≠ 容量

三件不同的事，三份库事实：

| 事实 | 表 | 含义 |
| --- | --- | --- |
| Worker 存活 | `workers.heartbeat_at` | 这个进程还在呼吸 |
| Run 所有权 | `run_leases.expires_at` | 这个进程仍是该 Run 的执行者 |
| 容量 | `workers.capacity` vs 该 Worker 的 ACTIVE 租约数 | 还能不能再领 |

三份事实，但 Worker 心跳与 RunLease 续租是**同一个定时器**（`CAIRN_WORKER_HEARTBEAT_MS`）：一次 tick 先写 `workers.heartbeat_at`，再续名下 RunLease。不为同一个定时器开两个变量。

恢复领取只看**租约过期**，不看心跳。心跳只用来把失联 Worker 标 `LOST`，并把它名下未关闭的 BrowserSession 标 `LOST`。短暂网络抖动不得仅因心跳漏一次就抢 Run。

`CAIRN_RUN_LEASE_TTL_SECONDS ≥ 3 × CAIRN_WORKER_HEARTBEAT_MS / 1000`，与会话租约同一条牙齿。  
`CAIRN_WORKER_LOST_AFTER_SECONDS > CAIRN_RUN_LEASE_TTL_SECONDS`，**严格大于**（默认 45 对 30）。「先丢租，再标人失联」必须由默认值兑现；两者相等意味着两件事同时发生，规则就只是一句话。

### D4. 同 ID 双开硬失败；重启自愈用新 `instance_id`

`CAIRN_WORKER_ID` 仍是部署标识（会话 `owner_worker_id` 已经用它），不是 UUID。每次进程启动生成 `instance_id`：

- 无行：插入 `READY`。
- 有行且 `heartbeat_at` 仍在丢失阈值内、`instance_id` 不同：启动失败，`WORKER_ID_CONFLICT`。这是唯一允许「两个进程抢同一个身份」被挡住的地方。
- 有行但心跳已过期：接管该 ID，写入新 `instance_id`，撤销该 ID 下残留 `ACTIVE` RunLease，对应 Run 进 `RECOVERING`（或按 D8 取消），再 `reconcileOwn` 会话。

开发默认 `local-worker` 只允许单进程。正式部署必须每实例唯一——冲突由注册检查卡住，不靠自觉。

**心跳写不进去之后不得留下僵尸进程。** `heartbeatWorker` 返回 `'ok' | 'lost' | 'instance_taken'`，两种失败的处置完全不同，压成一个 boolean 就只能一律自停，而自停之后没人能把 Worker 放回 `READY`（`claimRun` 要求 `status = 'READY'`），进程会活着却永不干活，且 worker 侧没有健康出口能暴露这件事：

| 结果 | 含义 | 处置 |
| --- | --- | --- |
| `ok` | 心跳已写入 | 续名下 RunLease |
| `lost` | 行不在，或状态已不是 `READY`（被同伴判失联） | 停手中止在途 → 用新 `instance_id` 重新注册（撤销自己残留租约）→ 恢复领取 |
| `instance_taken` | 该 ID 已属于另一个活实例 | 按本节「同 ID 硬失败」不得抢回：记错误日志并退出进程，交给编排重启 |

`lost` 必须自愈：一次网络抖动、长 GC 或主机挂起超过 `CAIRN_WORKER_LOST_AFTER_SECONDS` 就永久少掉一份集群容量，不可接受。自愈期间若 `registerWorker` 撞 `WORKER_ID_CONFLICT`（ID 被别人拿走），等同 `instance_taken`，同样退出。两条路都不允许「进程活着但永远不领取」。

### D5. 状态写入只有三种权威，先锁 Run 行再验租约

```text
grant     Worker 持有未过期 ACTIVE 租约（leaseId + fencingToken + holder）
recover   恢复扫描：行锁 Run 后确认无 ACTIVE（或 ACTIVE 已过期并就地过期），只允许收尾，不许写 SUCCEEDED
control   控制面：建 Run、取消（无租约状态直接终态，有租约状态只写 cancel_requested_at）、核查结论、认证恢复；永不写 Attempt 成功
```

**grant 与 recover 事务的第一条语句必须是 `SELECT ... FROM runs WHERE id = $1 FOR UPDATE`，`verifyRunLeaseForWrite` 在这把锁之后执行。** `claimRun` 的候选子查询与 D8 的过期 / 漂移处理同样锁 Run 行。

没有这把锁，「验完租约再提交」是 TOCTOU：谓词读到 `expires_at > now()` 之后、COMMIT 之前，回收扫描可以把租约置 `EXPIRED`，新 owner 可以领走并开始跑下一步，旧事务照样提交它的 `SUCCEEDED` 与 Run 终态。Run 行锁让接管、过期、提交三者串行化，验收第 8 条才有确定性可言。这也是 D12 锁顺序「先 Run 行 / RunLease，再 Session」在写路径上的落点：既有 `verifySessionLeaseForCommit` 与 `verifyRunLeaseForWrite` 是同一形状的谓词查询，都只能在这把锁之后调用。

P2 留下的写入入口，本期全部归类，一个不漏：

| 函数 | 权威 |
| --- | --- |
| `createRunWithSnapshot` | control |
| `requestRunCancel` | control（`QUEUED` / `RECOVERING` / `WAITING_FOR_AUTH` 无租约，直接 `CANCELLED`；`RUNNING` 只写取消请求；`NEEDS_REVIEW` 不接受取消，出口只有 review） |
| `reviewRun` / `resumeRunAfterAuth` | control |
| `claimRun` | 短事务内颁发 grant |
| `renewRunLease` / `releaseRunLease` | grant |
| `expireStaleRunLeases` / `sweepDriftedRuns` | recover（任何 Worker 可跑；每条 Run 一个事务，见 D8） |
| `startAttempt` / `finishAttempt` / `finishRunIfDrained` | grant |
| `markRunCancelled` / `failRunValidation` | grant 或 recover |
| `markRunWaitingForAuth` | grant；同一事务释放 RunLease |
| `failRunAuthTimeout` | recover（reaper，不持执行租约） |
| `reconcileOrphanAttempts` | grant（刚领到的新 owner）或 recover |

`skipRemainingStepRuns` / `cancelPendingStepRuns` 不得单独从 Engine 调用，只准嵌在上述事务里。

到期判定一律 `expires_at > now()`（库钟）。禁止用进程 `Date.now()` 当租约真相。

### D6. fencing 只增不回，过期不可原 token 复活

```text
fencing_token = 该 run_id 历史最大值 + 1     // 领取成功时
```

唯一 `(run_id, fencing_token)`。续租只延长 `expires_at`，不改 token。重新领取必须新行 + 新 token。旧 grant 的任何写入 0 行。

Engine / Lifecycle 持有进程内 `RunGrant`。续租失败立即作废 grant，abort 该 Run 的 signal，不再调用 `finishAttempt` 写成功。迟到的 Executor 回调若仍进来，`finishAttempt` 验租约失败 → `updated: false`。

Engine 既有 `watchCancellation` 在 Run 行离开 `RUNNING` 时 abort（≤ 250 ms 轮询）。D8 把丢租的 Run 翻成 `RECOVERING` 之后，它天然是「立刻停手」的第二条独立触发，与续租失败并列而不是替代。两条路径汇到同一个 AbortController，不得各自实现一套停手逻辑。

### D7. 领取与恢复同一个 `claimRun`，RECOVERING 优先

`claimRun` 一个事务两段：先试 `RECOVERING`，0 行再试 `QUEUED`。两段各是一条 `FOR UPDATE SKIP LOCKED`，都命中既有 `runs_claim_idx (status, created_at, id)`；不用 `ORDER BY CASE` 跨状态排序——那样用不上索引，RF06 压测时才发现就晚了。

```sql
-- 容量：inFlight.size < capacity，否则本 tick 不调 claimRun

-- 第一段
UPDATE runs
   SET status = 'RUNNING',
       started_at = COALESCE(started_at, now()),
       updated_at = now()
 WHERE id = (
   SELECT r.id FROM runs r
    WHERE r.status = 'RECOVERING'
      AND r.cancel_requested_at IS NULL
      AND NOT EXISTS (
        SELECT 1 FROM run_leases l
         WHERE l.run_id = r.id AND l.status = 'ACTIVE'
      )
    ORDER BY r.created_at, r.id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
 )
RETURNING *;
-- 0 行 → 第二段：同一语句，WHERE r.status = 'QUEUED'，去掉 NOT EXISTS
-- 同一事务：fencing = 该 run 历史最大值 + 1，插入 ACTIVE 租约，返回 RunGrant
```

`RECOVERING` 优先，避免已开工的 Run 被新 QUEUED 饿死。事务不持有到执行结束。

**不做 `(run, holder)` 幂等。** `claimRun` 没有 `runId` 入参，「同一 (run, holder) 已有 ACTIVE 则返回该 grant」在这条 SQL 上无从表达——已被本 Worker 持有的 Run 是 `RUNNING`，根本不在候选集里。防 tick 重入的责任在 Lifecycle：以 `leaseId` 去重，对同一 grant 不开两条 `execute`；容量判断用进程内 `inFlight.size`，不查库。同一 Run 至多一条 ACTIVE 由部分唯一索引卡住。

**毒任务护栏。** 一条稳定搞死 Worker 的 Run（OOM、后期浏览器步骤的原生崩溃）会被池子里每个 Worker 优先重领，挡住全部健康任务；D9 只拦 `SIDE_EFFECT`，只读步骤上的崩溃会无限循环。领取不做判断，判断在 D8：租约过期时若该 Run 的 `EXPIRED` + `REVOKED` 租约数已达 `CAIRN_RUN_MAX_RECOVERIES`，不再进 `RECOVERING`，直接 `NEEDS_REVIEW` 并挂 `RUN_RECOVERY_EXHAUSTED` 错误证据。`RELEASED`（`WAITING_FOR_AUTH` 主动让出）不计入。RF06 的 Echo Run 不会崩 Worker，压不出这个问题，所以要单测（验收第 17 条）。

### D8. 过期、漂移与取消抢先：每条 Run 一个事务

任何 Worker 可跑，幂等。先拿名单，再逐条收尾。

**候选（不锁，只是名单）：**

```sql
SELECT l.id AS lease_id, l.run_id
  FROM run_leases l
 WHERE l.status = 'ACTIVE' AND l.expires_at <= now()
 ORDER BY l.expires_at
 LIMIT $limit;
```

**逐条收尾（`settleLeaselessRun`，每条 Run 一个事务）：**

```sql
BEGIN;
SELECT status, cancel_requested_at
  FROM runs WHERE id = $run_id FOR UPDATE;              -- 与 grant 写入、claimRun 串行
UPDATE run_leases
   SET status = 'EXPIRED', released_at = now(), release_reason = 'lease_expired'
 WHERE id = $lease_id AND status = 'ACTIVE' AND expires_at <= now();
-- 0 行：别人已处理，ROLLBACK 跳过
-- 分流（同一事务）
COMMIT;
```

分流：

- 已是 `FINISHED` 或 `NEEDS_REVIEW`：只收租约，不动 Run。
- 有 `cancel_requested_at`：`CANCELLED`，未开始步骤 `CANCELLED`，在途 Attempt 按 D9 收尾。
- 该 Run 的 `EXPIRED` + `REVOKED` 租约数 ≥ `CAIRN_RUN_MAX_RECOVERIES`：`NEEDS_REVIEW`；在途 `RUNNING` Attempt → `FAILED`（`RUN_RECOVERY_EXHAUSTED`，`UNKNOWN`）；后续步骤保持 `PENDING`。
  口径：只数**失败的交接**。`EXPIRED` = 持有者失联，`REVOKED` = 上一代进程死了没释放、同 ID 重新注册时收走；`RELEASED`（含优雅停机的 `worker_shutdown`）不计。默认上限是 3，如果正常停机也计数，滚动发布三次就能把一条好端端的 Run 推进待核查。
- 否则：`RUNNING` → `RECOVERING`，等待 D7 再领。

过期与 Run 状态迁移**必须同一事务**。初稿把它们写成先批量 `UPDATE ... RETURNING run_id`、再逐条改 Run 两步：进程若在两步之间挂掉，租约已 `EXPIRED`、Run 仍 `RUNNING`，之后过期扫描找不到它（没有 ACTIVE 租约了）、`claimRun` 也不看它（只认 `QUEUED` / `RECOVERING`），永久卡死——正是本方案要消灭的那种状态。

**漂移扫描（`sweepDriftedRuns`）。** 同事务之外再加一道兜底，让 D2 的「`RUNNING ⇒ 恰好一条 ACTIVE`」自愈，而不是只靠验收第 3 条断言它不发生：

```sql
SELECT r.id FROM runs r
 WHERE r.status = 'RUNNING'
   AND r.updated_at < now() - make_interval(secs => $lease_ttl)
   AND NOT EXISTS (
     SELECT 1 FROM run_leases l WHERE l.run_id = r.id AND l.status = 'ACTIVE'
   )
 ORDER BY r.updated_at
 LIMIT $limit;
```

命中者逐条走同一个 `settleLeaselessRun`（无租约可收，只做分流）。宽限一个 TTL 是为了不和刚领取、尚未提交的事务抢；有 Run 行锁在，抢到也只是等待，不会错判。

不把「进程可能还活着」当成「已经被 fencing 停手」。旧进程醒来后续租 0 行，必须自己停。

### D9. 接管后先收孤儿 Attempt，再决定能不能续跑

新 owner 进入 `execute` 之前必须 `reconcileOrphanAttempts`：

| 现场 | 处置 |
| --- | --- |
| 无 `RUNNING` Attempt，有 `PENDING` 步骤，context 可从库重建 | 从下一个 `PENDING` 续跑（Echo / Delay / Fail 成立） |
| `RUNNING` Attempt 且步骤 `READ_ONLY` / `IDEMPOTENT` | 该 Attempt → `CANCELLED`；StepRun 保持可重试（回到 `RUNNING` 或维持，由下一轮 `startAttempt` 开新 `attempt_no`） |
| `RUNNING` Attempt 且步骤 `SIDE_EFFECT` | Attempt → `FAILED`（`UNKNOWN`），Run → `NEEDS_REVIEW`，后续步骤保持 `PENDING`，**不续跑** |
| 浏览器内存状态（页面、SPA） | 本期无浏览器步骤。P5 必须把「不能证明可重建」扩进本条，不得在 P3 假装已解决 |

Engine 现行逻辑会 `continue` 掉非 `PENDING` 的 StepRun。若不先收孤儿，接管后会跳过正在跑的步骤——这是 P3 必须修的行为。

`RECOVERING` 对 API 可见，表示「旧所有者已失效，尚未被新所有者接着跑」。领取成功后立刻回到 `RUNNING`，不要把 `RECOVERING` 做成人工状态。

### D10. `WAITING_FOR_AUTH` 释放执行槽；恢复走 control 再领取

`markRunWaitingForAuth` 与 `releaseRunLease(..., 'waiting_for_auth')` 同一事务。此后该 Worker 可以领别的 Run。

认领扫描**不得**领取 `WAITING_FOR_AUTH`。出口：

| 路径 | 结果 |
| --- | --- |
| `failRunAuthTimeout`（已有） | `FAILED` + `SESSION_AUTH_TIMEOUT`，跳过剩余步骤 |
| `POST /runs/:id/resume-auth` | 仅从 `WAITING_FOR_AUTH` → `RECOVERING`，审计；下一次 `claimRun` 增代领取 |
| `POST /runs/:id/cancel` | 无租约，控制面直接 `CANCELLED`（D5）；不等认证超时把一次人工取消写成 `FAILED` |
| 会话探针确认已登录（worker 侧可调同一 Repository） | 同 `resume-auth`，不另开状态 |

人工认证通道（headful / 扩展桥）仍不在本期；本期只把执行租约让出来，并给恢复入口。

### D11. `NEEDS_REVIEW` 只允许 fail / cancel，禁止恢复续跑

`POST /runs/:id/review`：

```ts
{ conclusion: 'fail' | 'cancel', note?: string }  // note 512 字内，进审计
```

- `fail` → `FAILED`，剩余 `PENDING` → `SKIPPED`
- `cancel` → `CANCELLED`，剩余 `PENDING` → `CANCELLED`
- 不得 `resume`。未知副作用一旦发生，平台不能证明「下一步是安全的」。要重做必须**新建 Run**。

**「不再自动推进」≠「已经结束」。** 现有 `runs.ts` 用一个 `TERMINAL_RUN` 集合（含 `NEEDS_REVIEW`）同时守 `requestRunCancel`、`finishAttempt`、`markRunCancelled`、`failRunValidation`。本期让 `NEEDS_REVIEW` 可以迁到 `FAILED` / `CANCELLED`，一个集合表达不了两件事，拆成两个谓词并进 `@cairn/shared`：

```ts
HALTED_RUN_STATUSES   = ['SUCCEEDED', 'FAILED', 'CANCELLED', 'NEEDS_REVIEW']  // 领取、Engine、finishAttempt 迟到回调：不得再动
FINISHED_RUN_STATUSES = ['SUCCEEDED', 'FAILED', 'CANCELLED']                  // reviewRun、requestRunCancel 幂等返回、控制台「还能不能操作」
```

不拆只有两种结局：`reviewRun` 被自己的守卫挡住，或某条迟到的 `finishAttempt` 覆盖掉已核查的结论。

`finished_at` 按 `FINISHED` 写，不按 `HALTED` 写：进 `NEEDS_REVIEW` 时不写完成时间，等 `reviewRun` 给出结论才写。否则同一条 Run 会先后写两个不同的完成时间，耗时统计也会把"停下来等人"算成"已完成"。

权限新码 `run:review`：admin 全部、operator 有、viewer 无。`PERMISSION_ACTIONS` 同步增补 `review`——它是封闭词表，今天没有任何校验引用它，正因如此更不能让它静默过期。系统角色由迁移补种（与 `session:dispose` 同一教训：目录有码、库没有绑定 = 按钮在、接口 403）。

`NEEDS_REVIEW` 对自动推进仍是暂停终态：领取不碰它，Engine 不碰它，`cancel` 也不碰它（原样返回，出口只有 review）。

### D12. 会话租约必须带 Run fencing；失联 Worker 把它的会话标 LOST

`acquireSessionLease` 的 `runFencingToken` 改为必填且 `≥ 1`。它的生产调用方是 `BrowserSessionManager.acquire(run: RunSnapshot, signal)`，改为 `acquire(run, grant: RunGrant, signal)`，token 从 grant 取，不从别处拼——这个中间层在初稿的文件清单里漏了。`ACTIVE` 行约束：

```sql
CHECK (status <> 'ACTIVE' OR run_fencing_token IS NOT NULL)
```

历史非 ACTIVE 的 NULL 可保留。`finishAttempt` 的提交边界顺序：先锁 Run 行（D5），再验 RunLease，再验 SessionLease。双 Lease 锁顺序：**先 Run 行 / RunLease，再 Session**；失败释放已占资源。本期 Engine 仍不 `acquire` 会话，但 Repository、`BrowserSessionManager.acquire` 签名与会话测试必须改完，避免 P5 再挖一次。

Worker → `LOST` 时：

```sql
UPDATE browser_sessions
   SET status = 'LOST', updated_at = now(), version = version + 1
 WHERE owner_worker_id = ANY($1)
   AND status IN ('CREATING', 'OPEN', 'CLOSING');
```

`markLostWorkers` 只动 `workers` 表并返回 id 列表；会话置 `LOST` 由 sessions repository 的 `markSessionsLostForWorkers(ids)` 完成。两个模块的写不混在一个函数里。

不关浏览器（控制面没有句柄）。出口仍是已有 `POST /browser-sessions/:id/dispose`。这是会话方案「P3 心跳判定 LOST」的回填，不是会话菜单。

### D13. 容量是本进程上限，不是集群调度

`CAIRN_WORKER_CAPACITY` 默认 `1`（与现在 `busy` 旗标同口径）。Lifecycle 改为 `inFlight.size < capacity` 才 `claimRun`。超员不报错、不排队，把 Run 留给其他 Worker。容量满是正常的 null，不是错误，不进契约枚举，只进日志字段。

Affinity（「有健康会话的 Run 必须回到 owner」）明确留给 P4 后半。本期任何 READY Worker 都可领 `QUEUED` / `RECOVERING`。

```sql
   SET status = 'REVOKED', released_at = COALESCE(released_at, now()),
       release_reason = COALESCE(release_reason, 'pre_0011_missing_run_fencing')
 WHERE status = 'ACTIVE' AND run_fencing_token IS NULL;
```

这些租约的持有进程早已不在，撤销是唯一诚实的处置。空库全量迁移证明不了这条，验收另列一项带存量数据的升级用例。

### `@cairn/worker`

```ts
// lifecycle
onBootstrap: registerWorker → 撤销自身残留租约 → sessions.reconcileOwn
tick (1 s): inFlight.size < capacity 则 claimRun → engine.execute(runId, grant, signal)；以 leaseId 去重
heartbeat tick (CAIRN_WORKER_HEARTBEAT_MS): heartbeatWorker + renew 名下 RunLease
session heartbeat tick（既有 CAIRN_SESSION_HEARTBEAT_MS）: renew 已有 SessionLease，不动
reaper tick（既有 CAIRN_SESSION_REAPER_INTERVAL_MS）: sessions.reap + expireStaleRunLeases + sweepDriftedRuns
          + markLostWorkers → markSessionsLostForWorkers
shutdown: DRAINING → 停领取 → abort 在途 → 等 Engine 收尾 → 释放仍 ACTIVE 的租约
          （若 Run 未终态：标 RECOVERING，供别人领；已由 Engine 写成终态则只释放）
```

`BrowserSessionManager.acquire(run, grant, signal)`：token 来自 grant（D12）。

**停机中止不是取消。** 外部信号（停机、被判失联后 fence）只说明本实例要走，Run 的事实没有结论：Engine 不写终态，直接返回，由 `yieldUnfinishedRun` 标 `RECOVERING` + 释放租约（`worker_shutdown`），未关闭的 Attempt 留给接管方按 D9 收敛。判据是外部信号 aborted 而「库里说停」（`cancel_requested_at`、Run 已离开 `RUNNING`）没有 aborted；两者都成立时取消优先。

这一条改掉了 P2 execution-kernel 的旧取舍（非副作用步骤停机按 `CANCELLED`）。P2 时没有 fencing、没有 `RECOVERING`、没有恢复领取，写终态是当时唯一能收口的做法；现在这三样都有了，"一次滚动发布把用户没取消的 Run 标成 `CANCELLED`" 只是让整套恢复能力在最常见的重启场景上永远用不到。

`SIDE_EFFECT` 仍按 P2：结果未知 → `NEEDS_REVIEW`，不得洗成 `CANCELLED`，也不走上面的交回路径——它在 Engine 里就有结论。kill -9 不依赖 `finally`，只依赖 TTL。

## 7. 验收

### L1 库与 Worker（S01 / RF06–RF08）

1. 空库迁移与上一版本升级通过；parity 含 `workers` / `run_leases` 列与部分唯一索引；`0011` 进入 `skipped`；`pnpm check:migrations` 通过。
1.1. **带存量数据的升级**：只装到 `0010`，写入一行 0008 形状的 `ACTIVE` + `run_fencing_token IS NULL` 会话租约，再往上升——`0011` 必须装得上，那一行变成 `REVOKED` + `pre_0011_missing_run_fencing`，之后新的 `ACTIVE` + NULL 仍被约束拒绝。去掉迁移里的补数据语句，本条必须以 23514 失败（负向验证过）。
2. 同 Run 并发 `claimRun`：只有一个 `ACTIVE`；另一个领到别的 Run 或 null；`fencing_token` 不重复。
3. 3 个 Worker 进程 × 100 条 Echo Run × 10 轮（RF06）：每个 Run 至多一个有效终态提交者；无重复 `SUCCEEDED`、无丢失（停在 `RUNNING` 且无 ACTIVE 超过 2 个扫描周期）。
4. 领取不做幂等：同一 Worker 连续两次 `claimRun` 领到两条不同 Run 或 null；直接插入同一 Run 第二条 `ACTIVE` 必须撞部分唯一索引。Lifecycle 对同一 `leaseId` 不开第二条 `execute`（单测）。
5. 续租：未过期且 holder / token 匹配则延长；过期、holder 不匹配、token 旧 → 0 行（返回 null，本进程停手；没有对应错误码，见 §4）。
6. 过期后原 token 续租与 `finishAttempt(SUCCEEDED)` 均拒绝；事实不变（F10-2）。
7. B 接管拿到 token 2 后，A 用 token 1 提交：`updated: false`，Attempt / context / Evidence 无新成功行（F10-3）。
8. A 提交与 B 接管在真实 PG 用屏障并发：grant 事务持 Run 行锁，只出现一种合法次序，不出现双成功（F10-4）。屏障放在 A 验完租约之后、提交之前，逼出 TOCTOU。
   屏障是 `finishAttempt` 的 `barrierAfterVerify` 测试钩子（与 `injectFailure` 同类），A 在「锁了 Run 行、验完租约、事实一行未写」处停住，回收在此期间闯入。**判据是屏障期间从另一条连接读到的 `runs.status` 仍是 `RUNNING`**：把 `lockRunRow` 从 `finishAttemptTx` 换成无锁读，这里会读到 `RECOVERING`（回收已提交），而 A 随后照样写出 `SUCCEEDED`——正是本条要挡的双成功。「先让租约过期、再并发提交」只能证明谓词会拒绝失效 grant，删掉行锁它照样通过，因此单列一条，不能用它冒充本条。
9. 重复完成回调：第二次 0 行或明确已关闭，不新建第二份 output Evidence（F10-5）。
10. kill Worker（RF07）：租约到期后 10 s 内另一 Worker 接管；安全样例（无在途 `SIDE_EFFECT`）跑完；旧 token 写入失败。
11. 暂停 Worker 超过 TTL：等同丢租；恢复后旧 grant 不能覆盖新 owner。
12. DB 断连：Worker 在库不可达期间继续执行（Delay 步骤），租约静默过期、被另一 Worker 接管；连接恢复后旧 grant 的续租与提交均 0 行，本进程停手；Run 无双成功、无双 Attempt 成功。
13. 在途 `SIDE_EFFECT` Attempt 未关时杀进程（RF08）：Run → `NEEDS_REVIEW`，不自动再执行该步；人工 review 后才终态。
    落测形状：留一个 `RUNNING` 的副作用 Attempt 不收尾（等同持有者被 kill 在这一步中间），租约过期 → `RECOVERING` → 接管方 `engine.execute`。判据是 Run 进 `NEEDS_REVIEW`、该 Attempt 记 `FAILED` + 「接管时副作用步骤结果未确认」、**后续步骤仍是 `PENDING`**、且进核查时交还租约（`run_halted`）。这是整套恢复里最危险的分支，此前只有 READ_ONLY 那条被覆盖。
14. 过期扫描幂等：连续两轮第二轮 0 行；`RELEASED` / `REVOKED` 不被改成 `EXPIRED`。
    判据落在具体那条租约上，不数全局行数（同一 schema 里还有别的夹具）：第二轮 `settleLeaselessRun` 返回 `skipped`，且该 Run 的租约行集合与第一轮后逐字节相同。
15. 过期与迁移同事务：注入「租约置 `EXPIRED` 后、Run 迁移前」故障，事务整体回滚，租约仍 `ACTIVE`；下一轮正常处理。
    注入点是 `settleLeaselessRun` 的 `injectFailure`（与 `finishAttempt` 的 `injectFailure` 同类），落在「租约已 `EXPIRED`、Run 已迁 `RECOVERING`、尚未提交」处——两边都写了才抛，才能证明是整单回滚而不是只回滚了一半。此前这条按代码形状根本测不了。
16. 漂移扫描：伪造 `RUNNING` 且无 ACTIVE 租约、`updated_at` 早于一个 TTL 的 Run → 一轮内 `RECOVERING` 并可被领取；带 `cancel_requested_at` 的 → `CANCELLED`；刚领取（`updated_at` 新鲜）的不被误判。
17. 恢复上限：同一 Run 连续 `CAIRN_RUN_MAX_RECOVERIES` 次租约过期后 → `NEEDS_REVIEW` + `RUN_RECOVERY_EXHAUSTED` 证据，不再被领取；`RELEASED` 不计入。
18. 启动自愈：伪造本 `CAIRN_WORKER_ID` 的 `ACTIVE` 租约与 `RUNNING` Run，启动后租约 `REVOKED`、Run `RECOVERING`（或按 D8 取消）。
    同一条用例一并钉住 D8 的计数口径：先走一次优雅停机（`yieldUnfinishedRun` → `RELEASED`），恢复次数必须仍是 0；再把心跳置旧、同 ID 重新注册，撤销残留租约，恢复次数才 +1，且旧 grant 从此续不上租。
19. 同 ID 且心跳仍新鲜的第二进程启动失败，输出不含密钥。
    两层：库层断言 `registerWorker` 抛 `WORKER_ID_CONFLICT` 且 message / stack 不含 `CAIRN_DB_PASSWORD`；Worker 层断言启动仍然失败，但先输出可读原因（是哪个 ID、多实例要一 ID 一实例、上一个实例死了要等多久），日志里不带凭证。`local-worker` 是默认值，本地开第二个必撞，这是开发者最先遇到的错误路径。
19.1. **心跳失败不留僵尸**：`lost` → 停手中止在途、以新 `instance_id` 重新注册、恢复领取（`isRunning()` 仍为真，不退出进程）；`instance_taken` → 不重新注册、退出进程；自愈时重新注册撞冲突 → 同样退出。三条各一个单测。
20. `WAITING_FOR_AUTH` 后该 Worker 能领到另一条 QUEUED；原 Run 无 ACTIVE 租约；`resume-auth` 后被领且 token 增代。
21. 容量 = 1 时第二份 grant 领不到（返回 null），不报 HTTP 错。
    单测形状：注入一条在途后调 `pump`，`claimRun` 一次都不许被调用（负向验证过：去掉 `inFlight.size >= capacity` 这行，用例失败）。
22. 失联 Worker 名下 `OPEN` 会话变为 `LOST`；`CLOSED` 不动；`GET /browser-sessions` 可见且 `disposable=true`。
23. 新 `ACTIVE` 会话租约缺 `runFencingToken` 被拒；`BrowserSessionManager.acquire` 不带 grant 不得编译通过；带 token 的提交边界：Run 丢租与 Session 丢租都不得写出 `SUCCEEDED`。
24. Echo → Delay → Fail 在无浏览器环境仍通过（RF04 不退化）；`engine.boundary` 仍禁止 `playwright` / `../browser`。
25. env：`LOST_AFTER ≤ TTL`、`TTL < 3 × HEARTBEAT` 均被 schema 拒绝，报错只含变量名。

## 9. 债务

1. 场景创建表单会让人误以为 Studio 已到。文案必须写「最小可运行定义」，不得出现「编排」「画布」。
2. `workers.id`、`run_leases.holder_worker_id` 与会话 `owner_worker_id` 都是 TEXT，没有 FK——会话表先于 `workers` 存在。不补 FK，避免跨迁移环；用测试保证失联更新能命中。
3. `RECOVERING` 窗口内页面会闪一下再回 `RUNNING`。不要为此加乐观合并；闪一下比假进度诚实。
4. RF06 压测吃 CI 时间。默认 `pnpm test` 跑缩小版（3 Worker × 20 Run × 2 轮）；全量 `pnpm test:rf06` 进 Gate，不得用缩小版宣称 RF06 通过。
   更要紧的是**进程维度整个缺失**：现在的「3 个 Worker」是单进程里的三行 `workers` 记录，共用一个连接池和一个事件循环，`pnpm test:rf06` 只是把数字调大。第 3 条要求的是 3 个 Worker **进程**。同理第 10 条（kill 后 10 s 内接管）、11（进程暂停超 TTL）、12（DB 断连注入）都需要真进程与故障注入，现在一条都没有：库层能证明「旧 token 写不进、租约过期会被接管」，但证明不了「进程被 SIGKILL / SIGSTOP / 断网时确实如此」。补这些要先决定测试基础设施（子进程编排 + 可注入的连接代理），属于独立一档工作，不该塞进本方案顺手做掉。在它落地之前，RF06–RF08 只能声明为「库层与单进程已验证」。
5. 双 Lease 锁顺序本期在 Run 一侧已由 `lockRunRow` 落地；Session 一侧没有真实 `acquire` 调用，只有签名与 Repository 注释。P5 第一次 `acquire` 必须加双锁集成测试。
6. 控制面 `resume-auth` 是声明式的：操作者说已经登录。平台不打开浏览器核对。错按会领到仍未登录的会话，P4/P5 的探针再失败。
7. `CAIRN_SESSION_REAPER_INTERVAL_MS` 现在驱动全部回收（会话、RunLease 过期、漂移、失联），名字过窄。改名是运维清理，不在本期。
8. `runs.lease` 把 worker id 暴露给所有 `run:read`。本期接受；若 Worker 命名日后携带部署拓扑信息，需要收到更高权限。
9. 恢复次数只累计、不随进度清零。一条跑了很久的 Run，即使每次接管后都推进了若干步，攒够 3 次失败交接照样进 `NEEDS_REVIEW`；而 D8 想抓的是「反复把 Worker 拖死、期间毫无进展」的毒丸 Run。改成「自上次有步骤成功以来的失败次数」是对 D8 的口径修订，要单独决定，不在本期顺手改。
10. 名称是连表取的当前值。历史 Run 的场景后来被改名，详情页显示的是新名字（步骤定义仍来自 Snapshot，不受影响）。要让展示也定格在当时，得往 Snapshot 里写入名称快照，属 P7 观察面的事。
