# Worker 登记与执行节点治理方案评审

日期：2026-09-14。对应方案：[Worker 登记、内部入口与执行节点治理](../spec/2026-09-14-worker-registry-and-fleet.md)。范围：方案全文、当前登记/心跳/停机/转发代码、共享契约、数据库升级约束与相关测试。

初评结论（针对修订前版本）：**方向认可，建议修改后再审。发现 3 项 P1、3 项 P2；原文本不宜直接作为扩容实施依据。** 本报告是技术评审，不代表用户批准方案。未实施 Worker Registry 或治理页，未改变 D0–D4。

2026-09-14 按用户要求修订方案：6 项问题及第 3 节补充边界已写入方案契约与验收项，详见第 5 节对照。当前状态为**方案已修订、待确认、未实施**；以下初评问题和行号保留为修订前 164 行版本的历史依据，不表示新文本仍未修订，也不表示代码缺口已经修复。

## 1. 可以保留的设计

- Worker 直接写数据库登记与心跳，API 保持无状态控制面；不引入 Worker → API 注册或执行事实回调。
- `workers` 保存登记，`browser_sessions` 保存 Session 事实，句柄数只作遥测；不另建 Session 账本，也不自动按句柄差改运行事实。
- API 仍通过受限内部通道转发，Web 不直连 Worker；不借治理页扩展远程桌面、热迁移或节点调度操作。
- 保留已有 Run/Session fencing、认证控制和处置审计，不把本线验收替代 D1 或 B 线的联合验收。

## 2. 需要修改的问题

### F1 · P1：自动登记监听地址会破坏跨主机 API 转发

**方案位置：第 5 节第 2 条、第 6 节优先级、WR03–WR05（66、78–83、150–158 行）。**

当前内部监听默认是 `127.0.0.1:8091`。按方案，没有 `ADVERTISE_URL` 就把这个地址写库；API 又无条件优先使用库内入口。API 扩到另一台机器或容器后，会请求它自己的 loopback。即使原先的 `CAIRN_WORKER_ENDPOINTS` 已指向可用的跨机 HTTPS 入口，也会被新登记的回环地址覆盖。因此，“两台 API 得到同一个字符串”不能证明它们都能连接 owner。

证据：[Worker 环境配置](../../packages/shared/src/env.ts)（86–88、609–615 行）、[内部客户端](../../packages/api/src/runs/worker-internal.client.ts)（49–98 行）。此外，[内部服务器](../../packages/worker/src/internal/http-server.ts)（1、24–41 行）目前只有 `node:http`，没有由监听参数推导 HTTPS 的能力。

**建议修改：** 分清监听地址与广告地址。分布式部署要求显式配置所有 API 均可拨号的 `ADVERTISE_URL`；没有广告地址时保留空值与旧映射，或将自动回环登记严格限定为显式的同机模式。补上 TLS 终止位置、证书信任和入口配置样例；直接写 `http(s)` 不能作为部署契约。WR03/04 至少覆盖不同网络命名空间的两个 API 实际访问同一 owner；同机不同端口样例只证明进程级转发。

### F2 · P1：失联阈值没有持久化，路由也没有检查心跳是否到期

**方案位置：第 4 节、第 5 节字段表、第 6 节第 1 条、第 8 节 `heartbeatFresh`（46、54–59、78、114 行）。**

方案要求按“该行登记时使用的失联阈值”计算 `heartbeatFresh`，但现有 `workers` 没有这个字段，计划只加 URL 和句柄数。现有 `registerWorker` 用**新申请者**传入的阈值判断旧实例；`markLostWorkers` 用**执行扫描的 Worker**的阈值判断所有实例。隔离验证中，旧实例配置 120 秒、心跳年龄 90 秒时，同阈值接管被拒绝，但新实例改用 60 秒便接管成功；60 秒的扫描也能提前将旧实例判 LOST。

同时，第 6 节只检查 `status === READY`。如果最后一台 Worker 死亡且没有其他 Worker 扫描，数据库行会继续保持 READY，API 不能据此认定登记仍有效。

证据：[workers 表](../../packages/db/src/schema/worker.ts)（12–22 行）、[registerWorker / markLostWorkers](../../packages/db/src/leases/leases.ts)（64–113、196–205 行）、[Worker 扫描入口](../../packages/worker/src/runtime/lifecycle.service.ts)（256–259 行）。

**建议修改：** 保存当前实例的失联策略或可验证的到期时刻，登记、续期、接管、失联扫描和 API 路由统一使用数据库时钟及同一到期规则；明确存量行的兼容值。路由必须同时满足状态、心跳和代次有效，失败不得走环境变量绕过。补“各节点阈值不同”“所有 Worker 停止后仍有 API”“到期边界”的用例。

### F3 · P1：接管验收漏掉旧进程迟到停机对新实例的写入

**方案位置：第 4 节接管约定与 WR02（47、149 行）。**

旧代次内部签名被拒绝，只能保护 HTTP 请求，不能保护登记表。当前 `onApplicationShutdown` 调用的 `markWorkerDraining`、`markWorkerStopped` 只带 `workerId`，没有 `instanceId` 条件。旧进程在超过失联阈值后仍停留于清理过程，或恢复后先收到停机信号时，可以把已经接管的实例标成 DRAINING/STOPPED。隔离验证已经复现：新实例 ID 保持不变，状态却被两次旧式停机调用改写，其下一次心跳返回 `lost`。

这是方案依赖的**既有实现缺口**，并非本次评审新增代码导致。由于本线明确支持接管和按状态选入口，应将修复列为前置或纳入实施范围。

证据：[状态写入](../../packages/db/src/leases/leases.ts)（178–193 行）、[停机流程](../../packages/worker/src/runtime/lifecycle.service.ts)（160–199 行）。停机还会按 Worker ID 重新加载全部 ACTIVE RunLease（192–195 行）；[该查询](../../packages/db/src/leases/leases.ts)（409–415 行）同样无法区分进程代次，须一起复核，不能只修状态更新。

**建议修改：** 所有实例自身发起的生命周期写入携带实例代次，并以数据库条件保证失配时不改行。旧进程的收尾只处理它原来持有的 grant，不能取得新实例的 grant 后代为释放。WR02 补“接管成功后旧进程继续心跳、执行停机清理”，验证新登记、入口和新 RunLease 均不受影响。单纯在写前查询实例 ID 不能替代原子条件。

### F4 · P2：`host:port` 加协议信息等价于完整内部 URL

**方案位置：第 8 节 URL 权限分层与 WR08（112、155 行）。**

第 5 节已经把 `baseUrl` 限定为无 path/query/fragment 的 origin。此时给 author 完整 `host:port` 和“是否 HTTPS”，便已经给出了重建完整 URL 的全部信息。隐藏 `baseUrl` 字段不能实现文中所说的入口信息隔离，WR08 仅检查字段缺失也不能证明它成立。

**建议修改：** 若确需限制内部入口信息，author 返回节点标识、计数和连接状态，真实 host/port/protocol 与 URL 统一按运维权限投影；若业务允许 author 查看真实 host:port，就直接承认其可知 origin，删除这条无效的安全承诺。列表和详情使用同一投影规则，不只限制列表响应。

### F5 · P2：遗漏已有 STOPPED 状态，无法完整表示正常停机节点

**方案位置：第 8 节状态词表、第 9 节页面状态（114、123 行）。**

共享 `WORKER_STATUSES` 实际是 `READY / DRAINING / STOPPED / LOST`，正常停机会写 STOPPED。方案一边要求沿用现有词表，一边只列三种状态。若按文中三值构建摘要 Schema，遇到正常停机行就可能验证失败；若前端只处理三值，也无法正确区分已停止和异常失联。

证据：[共享词表](../../packages/shared/src/run-lease.ts)（4–6 行）、[实际停机写入](../../packages/db/src/leases/leases.ts)（187–193 行）。隔离验证也确认 STOPPED 是现有 Schema 接受的合法值。

**建议修改：** 直接复用 `workerStatusSchema`，补 STOPPED 的列表、筛选、详情和显示优先级；将生命周期与心跳新鲜度分开表达。验收加入同一响应中同时存在四种状态的样本。

### F6 · P2：地址回退不足以覆盖现有数据库版本门禁下的滚动升级

**方案位置：第 3 节兼容说明、第 5 节迁移、WR05（31、54、152 行）。**

当前 API 和 Worker 启动时都会调用 `assertReady`；底层 `assertSchemaReady` 要求数据库迁移记录与进程携带的迁移清单完全一致。迁移到新版本后，已经运行的旧进程可能继续运行，但旧版本若重启或扩容，会被新增迁移记录拒绝；反过来，新版本在迁移前也不能启动。隔离验证通过增加一条迁移记录复现了启动检查失败。

证据：[API 启动检查](../../packages/api/src/db/db.module.ts)、[Worker 启动检查](../../packages/worker/src/db/db.module.ts)、[数据库版本检查](../../packages/db/src/migrate-native.ts)（75–101 行）。这不否定空入口时读取旧映射的功能，但不能由该功能推导出完整滚动升级兼容。

**建议修改：** 补明确的迁移/进程更新顺序、旧进程重启限制、回滚边界和版本兼容矩阵。可以采用受控维护窗口；若本期必须支持混合版本重启，则先设计并验证受约束的结构兼容策略，不能简单取消版本检查。WR05 分别验证“空入口兼容”和“真实旧版本在新库上的启动行为”。

## 3. 实施前还应写清的边界

这些是已有要求的落实点，不另计新的 P1/P2：

- **URL 校验须扩展，不能原样复用。** [现有校验](../../packages/shared/src/internal-auth.ts)（36–51 行）只检查协议与 HTTP loopback。探针确认 HTTPS 通配监听地址、userinfo、path/query/fragment 和 loopback 的 9222 端口均可通过。既然方案已经要求禁止或规范化这些输入，应列入 shared 的明确改动和 WR06。端口号本身不能证明服务身份，HMAC/代次和受限路由仍是必要门禁。
- **普通 Session 没有独立的 owner instance 字段。** [Session 表](../../packages/db/src/schema/session.ts)（29–43 行）只有 `ownerWorkerId` 和认证 hold 专用 `authHoldWorkerInstanceId`。第 6 节应分别写出普通观察、认证 hold 的代次校验来源；不要把认证字段当作所有 Session 都已有的归属信息。库内端点和签名代次应取自同一登记版本，不能跨两次查表拼接。
- **遥测需要未知值和采样时间。** 存量 Worker 没有上报句柄数时应是未知，不能用默认 0 制造“句柄泄漏/缺失”警告；按心跳采样的句柄数与实时槽位统计本来就可能短暂不同，应区分正常延迟与持续异常。未被回收的过期 ACTIVE SessionLease、HOLDING 与 WAITING_FOR_AUTH 的统计关联也须定义，避免“在跑”误导。认证关联应通过确切 Run/hold，不按 TargetAccount 关联任意历史等待 Run。
- **治理读取与降级需要有界契约。** 节点详情明确是否仅含未 CLOSED Session，以及筛选、分页或有界上限；补 `asOf`、入口来源和不泄露地址的降级原因。转发应明确连接/响应超时，失效登记不能仅等待底层长时间超时；不要为有副作用的认证输入增加自动重放。第 3 节“否则回退”应收紧为“身份和存活有效，仅入口为空时回退”，与第 6 节保持一致。

## 4. 实际验证范围

对照了宪法、主计划、B 线方案与相关实施代码、现有 Worker/租约测试、数据库支持说明和前端工作流。审查基于当前含未提交改动的工作区，不代表某个已发布版本。

另对当前源码执行 5 个隔离探针：临时 SQLite 文件由现有夹具创建并在结束时清理；共享包直接指向源码。未连接开发业务库、未启动正式 Worker 或浏览器、未请求外部服务。

| 探针 | 观察结果 |
| --- | --- |
| 不同接管阈值 | 120 秒阈值仍拒绝时，60 秒申请者已能接管 |
| 不同扫描阈值 | 60 秒扫描能提前判定采用 120 秒阈值的 Worker 失联 |
| 迟到停机 | 新实例被按旧 ID 的停机调用改成 DRAINING、STOPPED；新心跳返回 lost |
| 广告 URL 校验现状 | 上述非 origin / 通配 HTTPS / userinfo / 9222 样本被接受 |
| 升级后旧清单启动 | 数据库多一条迁移记录即被启动检查拒绝 |

执行结果：**5/5 探针完成并符合现状断言**。这些断言用于确认缺口，不是“修复已通过”或 WR01–WR09 验收通过。复跑材料见[探针说明](2026-09-14-worker-registry-repro/README.md)。

未执行 PostgreSQL/MySQL 复测、真实旧版进程滚动升级、跨机 API/Worker/TLS 联调或治理页验收。F1 的网络后果来自地址语义和源码分析；F3 的新 RunLease 清理风险来自调用链静态核对，探针只直接验证了登记状态覆盖。
