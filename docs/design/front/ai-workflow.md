# AI 前端开发工作流

更新：2026-09-24。适用：识途前端功能开发、界面调整与视觉评审。

目标：让统一效果由共用代码默认产生，在开发当次发现并修正偏差。本文只定义决策顺序与交付要求；颜色、组件细节继续由已有规范维护。

## 1. 当前认可的方向与工程状态

平台采用统一的浅色冷静蓝白（v1.6）设计基线。所有页面直接消费语义 Token 与基础组件；开发以现有真实已验收的代码为事实源与参考基准，不得翻找或继承已废弃的过渡期静态 HTML 原型。

| 资料 | 当前身份 | 使用方式 |
| --- | --- | --- |
| [Design Token](tokens.css) | 已接入生产的数值事实源 | 生产页面直接消费语义 Token，不写任意硬编码色值 |
| [组件规范](components.md)与 `components/ui/` | 状态契约与正式基础控件 | 复用公开 API、Radix 交互、微卡及弹窗视口约束 |
| [UI 设计语言](design-language.md) | 视觉签名、降噪、容器自适应与看板规范 | 设计界面排版、层次与控制项时遵守 |
| [前端落地约定](implementation.md) | 脚手架复用与约束 | 统一布局、分页底线与自动化测试保障 |

**日常优先参考已验收的真实代码**：
- [场景工作室 Studio](../../../packages/web/src/features/scenarios/studio-screen.tsx)：三栏弹性 Splitter、导轨步骤管线、受管画面投影与属性分段检查器
- [目标知识地图 Map](../../../packages/web/src/features/map/page.tsx)：海域全景与独立滚动详情抽屉
- [目标系统管理](../../../packages/web/src/features/targets/index.tsx)：冰川蓝集合摘要、表格工具栏与账号管理抽屉
- [识途助手 Dock](../../../packages/web/src/features/assistant/panel.tsx)：伴随停靠面板、思考折叠、引导卡片与动作胶囊
- [运行复盘 Run](../../../packages/web/src/features/runs/index.tsx)：结果轴、冻结快照与多层证据核对

## 2. 开发前先完成四项判断

新功能或实质交互改造在功能方案中用几行文字写清即可，不另建逐页规范。文案、格式与孤立装饰小改直接沿用已有任务和布局，不重复编写方案：

1. **任务**：用户来到这里要完成什么，主要业务对象是什么。
2. **主操作**：当前状态最值得用户采取的一个动作；该操作何时不可用。
3. **布局与复用**：选择下表中的页面组织方式，指出复用的布局和组件路径。
4. **状态与验证**：真实接口支持哪些状态，本次需要验证哪些正常与异常路径。

实现前阅读本文件，再按任务查阅 [设计语言](design-language.md)、[组件规范](components.md)、[落地约定](implementation.md) 和相关样板。不得从尚未迁移的旧业务页继承独立样式，也不得把早期原型的模拟逻辑当作真实功能契约。

## 3. 按任务选择页面组织方式

| 核心工作区 | 优先组织方式 | 关键约束 | 真实代码参考 |
| --- | --- | --- | --- |
| **步骤编排与调试 (Studio)** | 三栏弹性 Splitter 导轨：步骤管线 → 受管画面投影 → 属性/检查器/试跑 | 严禁页面横向滚动；受管画面固定投影比，步骤行高 32–36px，折叠非核心字段 | [场景工作室](../../../packages/web/src/features/scenarios/studio-screen.tsx) |
| **系统知识与地图 (Map)** | 顶栏状态与控制 → 知识海域全景 → 资产/安全路径抽屉 | 高度彻底隔离锁死；右侧资产列表仅内部滚动，严禁拉伸海域画布 | [目标知识地图](../../../packages/web/src/features/map/page.tsx) |
| **态势监控 (Dashboard)** | 顶栏紧凑控制带（指示灯+刷新器） → 核心指标卡 → 连续趋势图表流 | 杜绝大方框空洞堆叠；图表优先；定时轮询只静默更新 series，严禁全页闪烁 | [监控态势](../../../packages/web/src/features/maintenance/detail.tsx) |
| **智能助手 (Assistant Dock)** | 右侧伴随停靠面板（380–600px） → 思考折叠气泡 → 动作胶囊联动 | 主工作区必须容器自适应（`@container`）；空态提供 2 列分类微卡（≤68px） | [助手面板](../../../packages/web/src/features/assistant/panel.tsx) |
| **执行复盘与核对 (Run)** | 运行状态与耗时 → 执行录像 → 步骤列表（主截图可见） → Attempt 证据与判断 | 选中步骤与证据必须强联动；失败原因首屏直达；长日志不占满主屏 | [运行复盘](../../../packages/web/src/features/runs/index.tsx) |
| **对象查找与管理 (CRUD)** | 页面标题与操作 → 集合摘要 → 筛选与表格 → 详情抽屉 | 大数据默认服务端分页；勾选行不占用主操作位；右侧抽屉不重复列出已有属性 | [Target 管理](../../../packages/web/src/features/targets/index.tsx) |

这些是组合规则，不要求为三种布局各造一套框架。认证壳由布局提供：侧栏导航、底栏账号、顶栏全局搜索。新页面只组合 `Main` 与 `PageHeader`，不渲染顶栏。列表标题与侧栏 `title` 一致；详情才加 `PageHeader.parent`。优先扩展 `Main`、`PageHeader` 与已有组件，用 CSS Grid / Flex 组合。重复需求出现后再抽取共用组合。

新菜单三步：在 `sidebar-data.ts` 登记 → 页用 `Main` + `PageHeader` → 标题与侧栏文案一致。不要为新菜单改顶栏。

新增任务无法自然放入现有组织方式时，先为该局部做可操作样本并说明取舍。常规 CRUD、已有组件状态和现有布局的组合可以直接实施，不要求每个功能重复画 HTML。

## 4. 统一范围与自主空间

| 层次 | 规则 |
| --- | --- |
| 必须统一 | 色彩语义、字体刻度、控件尺寸与状态、焦点和动效、主操作层级、状态文案、领域对象含义；生产数值来自 Token |
| 可按业务决定 | 字段顺序、表格列、说明文案、分组、默认筛选、哪些低频设置折叠；保持核心步骤与证据可见 |
| 需要先展示局部效果 | 新的交互模式、改变既有导航方式、改变公共组件语义、为适配功能而调整整体设计方向 |

特定业务需要差异时，在该功能方案中说明原因、影响范围与复用位置。不要为一次特殊布局扩展全局规则，也不要在局部页面反复覆盖共用 Button / Input 的颜色和尺寸。

原型里的具体字号、边界和间距不是像素不变量。迁移时必须兼顾中文长内容、触控、键盘、对比度和真实数据密度；数值调整在共用 Token 或组件中完成，并用同一任务样本复核视觉效果。

## 5. 开发中的检查与交付

### 按影响范围使用验收 skill

[识途前端验收 skill](../../../.agents/skills/shitu-frontend-acceptance/SKILL.md)用于新页面、交互逻辑、布局与公共 UI 改造，或用户明确要求验收时。文案、无语义变化的展示格式与孤立装饰小改不自动触发；显式调用后也可以判为轻量检查并快速结束。

验收按轻量、局部、页面或底座分级。改按钮文案通常无需启动浏览器；改按钮提交行为需要验证结果；改公共 Button 或 Token 需要代表页面复核。金额精度、时区或权限即使只有一行变化，也要验证相关语义。分级细节只在 skill 维护。

### 自动检查负责明确规则

运行 `pnpm check:design`。现有检查覆盖 Token 引用、语义文字与集合摘要渐变对比度、输入边界、表面明度、文档链接、页面字号、TSX 硬编码色和 `transition-all`，并验证组件 HTML 样本的基础交互与布局。

该命令已接入 CI 配置，浏览器安装之后运行。它不能判断完整页面是否美观，也不等于真实 React 页面的视觉验收。类型检查、lint、已有功能测试继续执行；新增交互仅补实际需要的检查。

源码扫描的具体覆盖与例外见[落地约定](implementation.md#测试范围)。静态规则不等于穷举所有实现形式；skill 的触发描述也不等于程序化调度器。应在真实小改、局部交互和公共改造中观察验收范围是否适度，发现偏差再收紧相应规则。

### 浏览器检查负责实际效果

需要打开真实控制台时，先跑 `pnpm check:stack`（至少 `web` 范围）。栈未起来不得把 mock、单测或旧截图写成页面验收通过。

交互、布局或公共样式变更交付前，在浏览器打开实际实现，操作本次改变的主要路径；视觉变化需要查看渲染结果，截图范围随影响面缩放。轻量修改先做针对性检查，可能截断或有其他视觉疑点时再局部查看：

- 布局变化：至少检查主要桌面宽度与一个窄屏断点；影响共用布局时检查管理页和工作区。
- 状态变化：覆盖本次功能适用的正常、加载、空、错误、无权限状态；不为不存在的业务状态伪造交互。
- 内容变化：使用有代表性的中文长文本、较长列表、空值与错误说明；固定测试数据和时钟，屏蔽截图中的秘密信息。
- 公共组件变化：核对其相关状态，例如加载不跳宽、错误不清空输入、关闭弹窗焦点回到入口、减少动效生效。

截图差异用于发现变化，人工或 AI 复核变化是否合理。不能用“截图文件更新了”代替解释，也不能仅凭测试通过宣称视觉达到认可效果。

功能交付说明保持简短：**复用了什么、验证了什么、仍有什么偏差**；实际进行了浏览器验收时给可打开的页面或相关截图。轻量修改一句话即可，不强制另写验收报告。没有运行条件时如实说明缺口，不声称已经视觉验证。

### 识途必须保留的业务样本

只对涉及的模块运行这些案例，避免每次小改重复全平台测试：

- 未绑定 Target 的 Scenario 不可执行；AI 建议显式接受后进入可编辑草稿。
- Run 展示冻结快照；当前 Scenario 修改不改写历史解释。
- Attempt 失败、重试成功时，StepRun 与 Run 仍可以成功。
- 执行结果与证据完整性分别展示；补证据不能盲目重放业务操作。
- 副作用不明时提供核查路径；认证等待、无租约、连接中断有准确状态与动作。
- 目标账号与控制台成员分别表达，会话复用与租约占用分别表达。

### 交付前的双重视角自检清单（Double-Check Gate）

在声明前端开发或修改完成前，AI 必须通过本地浏览器仿真实际打开页面，并在心里以两重身份严格过审：

1. **普通业务用户视角自检（心智与易用性）**：
   - 页面上的词汇普通用户能否看懂？有没有出现内部枚举代码（如 `m_stress`、`stage-inspect`）、未转化的英文术语或自造晦涩辞藻？
   - 当前页面的第一核心主操作是否一眼可见？是否被次要或重复的按钮淹没？
   - 表单的必填项是否清爽（红色半角星号 `*`），而非粗暴的红色大汉字“【必填】”？
   - 弹窗在常见笔记本分辨率（如 1366×768）下，底部确认/取消按钮是否完整可见、无需艰苦滚动寻找？

2. **资深 UI/UX 设计师视角自检（布局、密度与对齐）**：
   - **紧凑度与对齐基准线**：并列子模块（如维护、采集、探索）是否有统一的栅格和对齐基准线？卡片是否过大过空？辅助列表类卡片是否压制在 56–68px 且不超过两列？
   - **Dock 伴随态动态响应**：打开右侧识途助手（380–600px）或详情抽屉时，主工作区的按钮和表格是否依然正常对齐？顶部工具栏次要按钮是否优雅收进「更多操作（...）」？
   - **长数据滚动隔离**：当列表有大量数据时，是否限制在自身内部滚动（`overflow-y-auto`）？严禁把页面其他图形画布拉成几千像素的长条！
   - **弹窗与复合行防重叠**：弹窗内 Checkbox / Radio 与右侧标题和说明文本是否保持间距？文本是否自动换行？有无任何元素重叠或横向溢出滚动？

## 6. 出现偏差时，修在产生偏差的位置

| 观察到的偏差 | 优先修复位置 | 复核范围 |
| --- | --- | --- |
| 多个页面的按钮、边框或阴影同时不协调 | 共用 Token / 基础组件 | 组件状态 + 管理页 + 工作区 |
| 只有某页内容拥挤、主次不清 | 该页分组、密度、布局组合 | 该业务任务与相关断点 |
| 运行状态、动作或证据关联错误 | 领域映射与组件组合 | 对应状态和真实功能测试 |
| 同一种问题反复出现 | 最小自动检查或一条通用规范 | 先证明检查能发现该偏差，再纳入常规命令 |

用户可以直接描述感受，例如“这张卡片太重”“主按钮不突出”“找不到失败证据”。AI 应先定位它属于公共规则、布局还是业务语义，给出局部修正并重新展示同一场景。一次局部反馈不扩散为全站改版；只有明确影响公共规则时才同步规范与跨页检查。
